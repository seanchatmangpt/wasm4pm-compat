# wasm4pm-compat v2030.1.1 — PRD / ARD

**Repository:** `seanchatmangpt/wasm4pm-compat`  
**Ecosystem role:** process-type-law / compatibility boundary  
**Release:** Chatman Ecosystem v2030.1.1  
**Standing conferred:** `UNKNOWN`.

## Product requirement

`wasm4pm-compat` SHALL remain the ecosystem's **structure-only process type foundry**. It defines bounded interoperable process-mining and process-intelligence types, admission/refusal semantics, deterministic projections, and graduation candidates without becoming the process execution engine.

The v2030.1.1 target preserves the existing fence: compatibility law is valuable precisely because it does not smuggle algorithm execution or production authority into shared types.

## Required capabilities

1. Express stable types for process/event/model interchange used across `process-intelligence`, `wasm4pm`, formal verification, gyms, and downstream products.
2. Preserve closed vocabularies and typed refusals for unsupported or malformed structures.
3. Maintain deterministic serialization and ordering for receipt-bearing projections.
4. Bind public standards and versions to compatibility types where applicable.
5. Provide positive, negative, drift, and replay fixtures for each graduated compatibility surface.
6. Keep `UNKNOWN`, `UNSUPPORTED`, `BLOCKED`, `BUILD_BROKEN`, `PARTIAL_ALIVE`, and `ALIVE` claim ceilings distinct.
7. Manufacture ggen-owned projections only from their canonical graph/query/template inputs.

## Architecture requirements

```text
public/process standards + admitted structural law
        -> canonical compatibility graph
        -> deterministic ggen projection
        -> structural admission / refusal
        -> exact-tree receipt + replay evidence
```

The repository SHALL NOT implement process-mining algorithms, unrestricted planners, network actuation, registry publication, or a hidden `wasm4pm` runtime. SELECT/CONSTRUCT structures may be represented; production DO is excluded.

## Verification architecture

The existing Gall-checkpoint and external-standing model remains normative. v2030 additions SHALL extend that model rather than bypass it. A type surface is not crown-complete because it compiles. Its owning structural, negative, generation, receipt, and replay gates must execute for the exact tree.

## Acceptance for v2030.1.1

- all exported compatibility surfaces have explicit semantic/version authority;
- deterministic committed projections reproduce from admitted source;
- unsupported structures return named `UNSUPPORTED` outcomes and policy/admission denials remain typed refusals;
- negative drift fixtures demonstrate that hand-edited/generated divergence is rejected;
- downstream `wasm4pm` and formal consumers can pin exact structural identities;
- no new path grants algorithmic or production actuation authority;
- exact-tree verifier evidence is available before any `ALIVE` claim.

## Falsifiers

The architecture is falsified if compatibility types require executing process-mining algorithms to establish ordinary structural validity; if a wrapper converts a refusal into success; if generated output can drift from its graph without detection; or if the crate becomes a second process engine.

## Ecosystem contract

`wasm4pm-compat` supplies **type law**. `wasm4pm` executes process behavior. `mfact` may certify formal properties. Runtime authority remains external. This repository's maximum claim is bounded by its own external verifier and exact-tree evidence, consistent with its repository contract.
